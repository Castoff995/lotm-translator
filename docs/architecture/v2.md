# LOTM Translator Architecture v2

Architecture v2 is the normative architecture for new development. The
existing `src/lotm_translator/` package is v1: a prototype and future benchmark
baseline. It remains usable, but new domain concepts do not belong there.

## Goal

The eventual system converts a Chinese original, official English translation,
and Russian translation into a reviewed trilingual corpus for training a local
translation model:

```text
source files -> ingest -> normalized corpus -> pairwise alignment
-> trilingual reconciliation -> confidence/review -> confirmed alignment units
-> semantic grouping -> training blocks -> quality gates -> training dataset
```

Task 001 implements only Phase 0–2: foundation and the manually editable gold
format. It does not implement alignment algorithms or training export.

## Fundamental entities

- **Paragraph** is a physical paragraph from one source. Its stable identity is
  independent of every alignment algorithm.
- **AlignmentUnit** answers only which source paragraphs correspond. It may be
  many-to-many and may contain an explicit gap.
- **TrainingBlock** is a later grouping of one or more confirmed alignment
  units that should be shown to a translation model together.

`AlignmentUnit` and `TrainingBlock` are different truths. Alignment must never
silently create semantic training boundaries. Gold `JOIN`/`BREAK` annotations
are independent labels for the future grouping subsystem.

## Source hierarchy

1. Chinese original: primary source of meaning.
2. Official English: semantic auxiliary source.
3. Official Russian: primary Russian target and style reference.
4. Fan Russian: secondary reference only.

Future primary alignment directions are ZH↔EN and ZH↔RU. EN↔RU is an
additional consistency signal. Source role is declared by a versioned manifest,
never inferred from a directory name.

## Layers and boundaries

- `domain`: stable IDs, typed corpus entities, source descriptors and provenance.
- `ingest`: source file to immutable raw chapter bytes/text and manifest link.
- `normalize`: conservative, versioned raw paragraphs to normalized paragraphs.
- `infrastructure`: centralized path policy and serialization boundaries.
- `gold`: human-editable alignment truth, boundaries, drafts and validation.
- Future `alignment`, `reconcile`, `review`, `grouping`, and `training` layers
  are documented but intentionally absent until their phases begin.

Ingest does not align, group, judge, or translate. Normalization does not remove
story-like content. Gold alignment references paragraph IDs and does not own a
second copy of paragraph text.

## Immutable raw data and provenance

The data flow is one-way:

```text
immutable raw source -> versioned normalization -> downstream representations
```

An ingest operation may create a raw chapter or verify that identical content
already exists. It must reject attempts to overwrite the same raw location with
different bytes. Every normalized paragraph stores its raw location, raw
paragraph index, source manifest, checksum, and normalization version.

Conservative normalization permits Unicode normalization, newline/whitespace
normalization, and deterministic technical cleanup. Suspected footnotes,
translator notes, cultural explanations, headings, separators, and metadata
remain present and are classified or flagged. They are never silently deleted.

## Alignment, review and confidence

Pairwise alignment precedes trilingual reconciliation. Confidence is evidence
for review, not permission to mutate source truth. Human confirmation produces
gold truth. Explicit gaps represent additions, omissions, translator notes, and
edition differences without fake paragraphs.

## Reproducibility

Manifests, normalized documents, and gold documents are schema-versioned.
Stable paragraph IDs are deterministic and human-readable. Serialization is
centralized, JSON is UTF-8 and pretty-printed, and validators reject incomplete
or contradictory gold data. Algorithms, models, and caches never affect IDs.

Machine-readable contracts are stored in `schemas/v2/`. Runtime dataclasses and
explicit IO codecs enforce the same model without requiring a JSON Schema
library in the foundation environment.
