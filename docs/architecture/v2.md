# LOTM Translator Architecture v2

Architecture v2 is the normative architecture for new development. The
existing `src/lotm_translator/` package is v1: a prototype and future benchmark
baseline. It remains usable, but new domain concepts do not belong there.

## Goal

The eventual system converts a Chinese original, official English translation,
and Russian translation into a reviewed trilingual corpus for training a local
translation model:

```text
source files -> ingest -> normalized corpus -> pairwise alignment
-> trilingual reconciliation -> confidence/review -> confirmed alignment units
-> semantic grouping -> training blocks -> quality gates -> training dataset
```

The current implementation covers Phase 0–2 foundation, Gold review, the Task
004 structured-EPUB amendment, and Task 004A canonical Source Chapter Maps in
Phase 1. It does not implement alignment algorithms or training export.

## Fundamental entities

- **Paragraph** is a physical/editorial paragraph from one source, never a
  sentence or a future alignment unit. Its stable identity is independent of
  every alignment algorithm.
- **AlignmentUnit** answers only which source paragraphs correspond. It may be
  many-to-many and may contain an explicit gap.
- **TrainingBlock** is a later grouping of one or more confirmed alignment
  units that should be shown to a translation model together.

`AlignmentUnit` and `TrainingBlock` are different truths. Alignment must never
silently create semantic training boundaries. Gold `JOIN`/`BREAK` annotations
are independent labels for the future grouping subsystem.

## Source hierarchy

1. Chinese original: primary source of meaning.
2. Official English: semantic auxiliary source.
3. Official Russian: primary Russian target and style reference.
4. Fan Russian: secondary reference only.

Future primary alignment directions are ZH↔EN and ZH↔RU. EN↔RU is an
additional consistency signal. Source role is declared by a versioned manifest,
never inferred from a directory name.

## Layers and boundaries

- `domain`: stable IDs, typed corpus entities, source descriptors and provenance.
- `ingest`: source file to immutable raw chapter bytes/text and manifest link.
- `normalize`: conservative, versioned raw paragraphs to normalized paragraphs.
- `infrastructure`: centralized path policy and serialization boundaries.
- `gold`: human-editable alignment truth, boundaries, drafts and validation.
- `review`: Phase 2 local UI and application service that display normalized
  paragraphs, capture explicit human annotations, and validate/persist drafts.
- `hints`: optional Phase 2 assistive providers/cache for paragraph-internal
  translation, segmentation and lexical span correspondence. Hints are not
  corpus truth and have no Gold write access.
- Future model-assisted alignment review, `alignment`, `reconcile`, `grouping`,
  and `training` layers remain absent until their phases begin.

Ingest does not align, group, judge, or translate. Normalization does not remove
story-like content. Gold alignment references paragraph IDs and does not own a
second copy of paragraph text.

The Phase 2 `review` package is deliberately human-only. It MAY display source
truth, capture selections/GAPs/boundaries, validate, save, resume, undo and
rollback. It MUST NOT infer, rank, recommend or auto-accept semantic
correspondence. The future Phase 5 review subsystem may present model evidence;
that is a separate capability and does not change human Gold truth implicitly.

The narrow `hints` exception does not make Review an aligner. Review MAY request
and visualize local ZH→EN machine hints, Chinese segmentation, and soft lexical
ZH↔EN span correspondence inside one already displayed ZH Paragraph. It MUST
label them non-canonical and MUST NOT use them to select/rank physical Paragraph
correspondence or create/modify AlignmentUnit, GAP, ParagraphDisposition,
JOIN/BREAK, cursors, normalized corpus, or source truth. The dependency is
one-way: `review UI -> hints API -> local models/cache`; `hints` does not import
or call the Gold mutation service.

Paragraph alignment remains Phase 3 corpus-level correspondence between
physical Paragraphs. Lexical hint alignment is only a Phase 2 visual mapping
between token/spans within one ZH Paragraph and its temporary machine-generated
EN hint. Lexical scores are not Gold evidence and do not flow into Phase 3.

## Immutable raw data and provenance

The data flow is one-way:

```text
immutable raw source -> versioned normalization -> downstream representations
```

An ingest operation may create a raw chapter or verify that identical content
already exists. It must reject attempts to overwrite the same raw location with
different bytes. Every normalized paragraph stores its raw location, source
manifest, checksum, normalization version, and a tagged provenance location:
an exact 1-based line span for text/OCR or exact DOM fragments for EPUB.

Each source declares how physical paragraphs are recovered:

- `blank_lines`: consecutive non-empty lines between blank lines;
- `one_per_line`: each non-empty raw line is a physical paragraph;
- `manual_spans`: a separate versioned, human-editable map from raw line spans
  to physical paragraphs or explicit exclusions.
- `epub_structure`: a registered structural artifact maps an explicit
  spine-ordered chapter slice to XHTML DOM fragments.

`manual_spans` is deterministic preprocessing, not alignment or semantic
grouping. Its boundaries are decided from that source and, for OCR, its source
pages. A confirmed artifact is frozen in the source manifest by path, version,
and checksum, and the same provenance is copied into the normalized chapter.
Changing confirmed segmentation requires an explicit source revision/new
`source_id` and regeneration; an existing paragraph ID must never silently
refer to different text.

For structured EPUB, the immutable authority is the complete `.epub` package,
not a flattened TXT extraction. EbookLib reads the container, package, spine,
EPUB2 NCX and EPUB3 navigation; strict lxml parsing resolves the confirmed DOM
selectors. Navigation proposes chapter slices but is not re-run as truth during
normalization. The registered artifact freezes package/document/fragment
checksums, spine indices, DOM paths and optional in-element offsets. A checksum,
selector, tag, ID, ordering or coverage mismatch fails closed. Details are in
[`epub-ingestion.md`](epub-ingestion.md).

Canonical chapter identity is resolved separately from source-local numbering.
`ChapterId.number` is always the global corpus chapter. A frozen, source-level
Chapter Map records source chapter ordinal, numbering scope, local number, and
exact TOC locator for every navigation entry without changing Paragraph IDs.
See [`chapter-identity.md`](chapter-identity.md).

Conservative normalization permits Unicode normalization, newline/whitespace
normalization, and deterministic technical cleanup. Suspected footnotes,
translator notes, cultural explanations, headings, separators, and metadata
remain present and are classified or flagged. They are never silently deleted.

## Alignment, review and confidence

Pairwise alignment precedes trilingual reconciliation. Confidence is evidence
for review, not permission to mutate source truth. Human confirmation produces
gold truth. Explicit gaps represent additions, omissions, translator notes, and
edition differences without fake paragraphs.

Every physical paragraph receives exactly one explicit human Gold fate: either
membership in one AlignmentUnit or a non-alignment `ParagraphDisposition`.
Dispositions reference stable paragraph IDs and never arise automatically from
ParagraphType. They are not GAPs: a GAP describes an absent side of a real
alignment correspondence, while a disposition excludes an existing paragraph
from translation alignment after human review.

## Reproducibility

Manifests, normalized documents, and gold documents are schema-versioned.
Stable paragraph IDs are deterministic and human-readable. Serialization is
centralized, JSON is UTF-8 and pretty-printed, and validators reject incomplete
or contradictory gold data. Algorithms, models, and caches never affect IDs.

Machine-readable contracts are stored in `schemas/v2/`. Runtime dataclasses and
explicit IO codecs enforce the same model without requiring a JSON Schema
library in the foundation environment.
